## D1：独立隔离验收准备

1. 把总计划 A01–A16 映射到测试文件、环境和证据；不以既有通过数量代替新语义。
2. 准备独立 API/PostgreSQL/Web 验收环境与假口令，不连主开发库执行建事实、清库或恢复。
3. 测试项目名/端口/缓存/浏览器档案隔离。运行产物位于当前版本 `.runtime/test-artifacts/stage3-deepseek`，最终证据归 `stage3-final`。
4. 设计浏览器故障流程：请求发出后丢回执/刷新；已成功后改草稿；成功 JSON 损坏；存储写入失败；双页面旧版本提交。正常写入必须落真实隔离 PostgreSQL。
5. 用当前允许的浏览器工具/受支持测试设施执行，不能私自绕过环境的浏览器控制规则。缺少支持时交由 Codex 接入运行设施，不以无 DOM 测试假称 E2E。

## D2：最终发布验证

1. 新建 `scripts/release/verify-mvp.sh` 编排发布验证；由 Codex 接入所需共享配置。它是本阶段待实现命令，不能只创建空壳输出成功。
2. 覆盖 MVP 默认模式、AI 直接 API 禁用与无外部调用；development + mock 的旧 AI 回归继续通过。
3. 通过界面完成模块/模板/任务/指标/成就与真实记录闭环，验证 5→10 分钟门槛、去重、null/0、删除证据后复核。
4. A07–A12 做浏览器实际交互与数据库事后核对；最重要的断言是只有一条事实、同一操作能确认、用户输入没有被吞或静默覆盖。
5. 验证从浏览器下载的数据导出；在空隔离库恢复并重新读取，比较事实、墓碑、修订、回执。不要对主开发库使用 `--allow-development`。
6. 重启隔离应用检查数据持续可读；不要为了验收强制重建用户的开发 PostgreSQL 容器。
7. 360px 实际浏览器打开/输入/提交；缺真机时明确仅视口模拟，不把它写成手机联网、离线或同步已交付。
8. 输出每项 PASS/FAIL/SKIP，强制项 SKIP 或未运行不能计入最终通过。新版本不能只因 CLI exit 0 就忽略日志内跳过。

既有 `verify-browser.mjs` 是宿主侧冒烟、会读取开发配置；不能直接拿它跑开发库后称为隔离发布验收。可参考场景，但新增验证必须使用隔离地址、假口令和专用档案。
