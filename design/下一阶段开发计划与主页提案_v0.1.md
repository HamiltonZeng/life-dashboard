# 人生面板：下一阶段开发计划与主页提案 v0.1

状态：供下一轮开发采用的提案；本轮没有实现这些功能，现有首页继续留空。

## 1. 下一阶段的目标

建议把下一阶段定义为：**可以在手机上可靠记录，并在电脑查看同一份数据；任务、数值和成就能解释自己的来源；AI 可以失败，但记录不会因此丢失。**

以“用得住”为第一关口，再做主页游戏感和更复杂玩法。继续使用 PostgreSQL、独立 API 和本地 Docker；当前不需要立即租 VPS。以后部署成本仍沿用每月 40 元以内的 VPS 目标，实际容量与性能需在接近部署时测量，AI/域名/备份费用单列。

阶段编号沿用旧规划；以下 S0–S5 是新的执行批次，不代表旧 T2/T3 已全部完成。工期应在每批任务卡确认后估算，不把多个模型同时开工等同于工作量按比例下降。

## 4. 手机、多端与数据库设计

### 4.1 权威数据与本地缓存

PostgreSQL 继续作为统一事实来源。Web、未来手机 App、桌面应用均通过 `/api/v1` 访问；不要让 App 直接连接 PostgreSQL，也不要为每个端复制不同的成就算法。

浏览器端 IndexedDB 负责草稿、缓存和待发送命令。页面必须区分“已保存本机”“等待同步”“服务器已确认”“冲突待处理”，不能显示一个含糊的“保存成功”。计数和成就的权威结果由服务端返回；离线预览如有展示，明确为暂估。

服务器存储仍在当前版本目录，持久数据、备份和可清理缓存分区说明。新版本数据库迁移先备份，在隔离副本验证；不让两个版本的 PostgreSQL 进程同时打开同一物理数据目录。手机浏览器缓存由手机操作系统管理，无法强行存进电脑版本文件夹。

### 4.2 最小同步协议

建议先实现记录同步，稳定后再把模块与定义写入纳入同一协议：

| 接口/对象 | 建议语义 |
| --- | --- |
| device | 服务端注册设备 ID、撤销状态、最后 ack；与正式会话关联 |
| push | 命令含 operation_id、设备、实体 ID、base_version；返回逐条确认/冲突 |
| pull | 按用户单调 seq 获取变更；游标不使用客户端时钟 |
| ack | 设备确认收到游标；可重复；服务端据此决定保留与清理策略 |
| reset/snapshot | 游标过旧时返回明确重建信号；保留尚未确认 outbox，避免覆盖未发送事实 |

同一次用户操作在超时重试、刷新和重连后沿用同一 operation_id。409 要保留本地版本并显示差异，不自动以最后写入覆盖。删除保留 tombstone，防止另一设备旧记录复活。

change_log 已有基础，但还需确定：哪些实体参与同步、完整字段与隐私、顺序与批次边界、分页游标、收件确认、日志保留、会话撤销和版本不兼容。不能只新增三个路由就宣称同步完成。

### 4.3 手机访问路径

本地先完成电脑为服务端、手机为客户端的可信 HTTPS 入口，处理固定地址、同源、Secure Cookie 和设备授权。当前 localhost 对手机指向手机自身，不能直接复用电脑地址；电脑睡眠或关机时也无法接收同步。

手机离线记录依赖缓存外壳与本地队列。电脑不在线时可先记本机，服务恢复后再同步。外网随时在线需要后续稳定服务端或部署方案，不把“本地持久化”写成“任意地点实时在线”。

## 5. AI、报告、长期归档与 RAG

### 5.1 配置生成和数据分析分成两类任务

保留当前模型 adapter 抽象，但为不同任务使用独立输入/输出 Schema：

- `module_blueprint`：生成配置，必须经过校验与预览/原子应用。
- `daily_report` / `weekly_report`：解释确定性统计与相关文本，不直接改事实。
- 后续“建议转任务”：报告建议经用户采纳，生成一条有来源的配置命令，不能由模型直接悄悄完成任务。

真实调用前确认所选模型与结构化输出行为，用最小样本测试 create/extend、格式错误、截断、限流和余额不足。密钥仅保留服务端；记录 provider、model、提示版本、token 用量与估算费用。不要通过浏览器暴露密钥。

### 5.2 后台工作与成本

复用 PostgreSQL 的队列方案即可，无需当前增加 Redis。可按原规划引入 pg-boss，但先确认任务状态与数据库事实的一致性：任务唯一键、领取租约、重试次数、取消请求、进程崩溃恢复、幂等应用。

需要同时区分任务数限制、token 上限、估算预算预留和实际用量。HTTP 重试不等于供应商不会重复计费；对结果未知的外部调用保留状态和审计，不盲目无限重试。默认手动生成报告，定时生成由用户配置，缺少事实时跳过或明确“记录不足”。

### 5.3 报告生成链路

建议链路：

```text
已确认且未删除的原始记录
  → 服务端 SQL/领域规则确定性聚合
  → 统计快照 + 有范围的相关文本 + 来源 ID
  → 模型解释与建议（严格 JSON）
  → 数字/引用校验
  → 版本化报告 + UI 展示
```

报告建议保存 report_type、用户当地周期、时区、源数据截止游标、统计规则版本、提示版本、模型、结构化输出、用量、生成时间与状态。来源记录及当时版本可通过引用表关联。相同输入快照可复用结果，避免每次打开首页重新付费生成。

历史记录变更时，把受影响报告标记 stale，允许重生成但保留旧版本与当时依据。晚补记录以 occurred_at 归入业务周期，以变更游标识别“原报告后新增”；不能只按 created_at 归档。

长数据先按时间范围/模块查询、做日周月统计，原始记录保持可追溯。派生汇总是可重建缓存，报告是带版本的分析产物，备份是独立恢复副本；三者不能互相替代。日志保留清理必须考虑设备 ack 与最旧允许恢复的游标。

### 5.4 当前是否做 RAG

**日报周报第一版不需要向量 RAG。** 热量合计、训练次数、支出和任务完成等问题，应由可信规则算出，再让模型解释。把所有记录切片后检索，不能保证得到完整统计，反而容易漏算。

先采用“结构化查询 + 相关文本检索”：限定用户/时间/模块后，用 PostgreSQL 全文检索或标签筛选找回反思文本。多年笔记出现“我在什么情况下最容易拖延”这类跨时期语义问题时，再评估 pgvector；用固定问题集比较召回率和成本后决定。

如后续加入向量层，要保存来源 ID、记录版本、切片与 embedding 版本，编辑/删除后更新索引；检索先按用户权限过滤，结果回链原文。用户删除的数据不得继续通过旧向量被召回。索引是可重建派生数据，不能成为唯一存档。

## 6. 主页的三个方向

| 方向 | 内容与感受 | 优点 | 代价 |
| --- | --- | --- | --- |
| A：轻量营地（推荐） | 今日重点、快速记录、四模块入口、少量真实进度 | 有游戏入口感，手机操作短，和现有五面板自然连接 | 需控制卡片数量并解释同步状态 |
| B：角色档案 | 自定义角色名、模块属性、历史轨迹、成就陈列 | 更像游戏角色界面，适合长期反馈 | 容易把不完整记录包装成“能力分数”，需额外规则 |
| C：工作台 | 今日任务、周趋势、数据质量、AI 复盘 | 信息密度高，适合电脑分析 | 手机容易拥挤，重复五面板内容 |

建议 A 做默认首页，把 B 的外观和 C 的少量可选组件放入后续个性化。首页承担“从哪里开始”，详细编辑仍进入独立面板；所有组件遵循当前模块筛选、任务关联和返回上下文规则。

## 7. 推荐首页：轻量营地

### 7.1 信息顺序

手机首屏先看到当前日期/当地周期、简洁同步状态、一项今日重点，以及“记一条”。之后再放模块卡片、进度与报告。桌面可左右分栏，但不改变语义与操作顺序。

```text
营地                               同步：已确认 / 待发送 N
当地日期                           [记一条]

今日重点：用户选定的一项任务
[去记录 / 手动完成 / 查看规则]

学习与发展        饮食与锻炼
财富与收获        娱乐和交际
（每卡只固定 1–2 个用户选定指标）

本周真实进度 / 最近成就 / 复盘入口（可选组件）
```

“今日重点”优先由用户固定，不让 AI 每次刷新改写优先级。未设置时提供“选择今日重点”；没有任务时可直接记录，无需先创建任务。快速记录从模块/最近模板进入，已确认内容和草稿要明确分开。

### 7.2 四模块卡片

- 学习与发展：可固定“本周记录分钟数”“本周学习次数”，点击进入来源或模块记录。
- 饮食与锻炼：现阶段可展示运动随记次数；营养结构化上线后才展示 kcal、蛋白质等。
- 财富与收获：现阶段显示收获记录；账本上线后才展示统一币种与口径的收支。
- 娱乐和交际：活动次数、用户主动填写的体验；不根据聊天数量推断社交能力。

每张卡显示统计窗口和单位，无数据时显示“暂无记录”或留出记录入口，不自动按零判定表现差。自定义模块也能固定在首页；默认四模块不应写死在前端数据结构里。

### 7.3 游戏感的边界

建议通过地图式模块入口、色彩、成就徽章和轻动效表达游戏感。等级/经验若加入，必须显示规则版本、来源记录与上限；它是记录系统内的反馈，不能宣称代表人的真实智力、健康或财富能力。

避免第一版就做统一“人生总分”、强制连续打卡惩罚、随机奖励或排行榜。四模块单位不同且记录缺失程度不同，不能直接相加形成看似客观的分数。可改用用户自定目标的分项进度：每项进度均有周期、来源和可修改目标。

删除证据时沿用现有待复核规则；首页不能继续显示已失效的“本周完美完成”。动画可关闭，手机减少动效默认跟随系统。

### 7.4 报告与建议

首页只展示最近一次日报/周报的生成时间、覆盖周期、是否过期和一句有依据的摘要。生成按钮手动触发；未接入时隐藏组件或明确未启用，不显示虚构 AI 分析。

建议最多展示 1–3 条，并可以点开依据；“转为任务”需要明确采纳，任务保留 report_id 来源。报告不自动填补缺失热量、资产或心情。

## 8. 首页所需的最小契约与验收

提议新增用户主页偏好：组件顺序、固定模块、每模块固定 metric ID、今日重点 task ID、显示设置。优先存服务端并参与同步，设备布局可本地单独保存。今日重点按用户当地日期定义，跨午夜重新选择规则明确。

主页可提供一个聚合读取接口，返回数据截止游标、任务摘要、选定指标、最近授予和报告状态；计算复用现有领域规则，不在浏览器复制一套统计。初期不需要单独建“主页事实表”。

验收标准：

1. 从首页进入常用模板不超过两次点击，不计输入与首次登录。
2. 未登录、空库、全模块停用、网络失败、离线待发送、冲突都能明确呈现。
3. 数值能解释单位、周期和来源，null 不显示为 0，时间按用户时区处理。
4. 今日重点跳转携带绑定信息，不预填真实完成事实，返回恢复上下文。
5. 改写/删除证据后，主页与面板一致刷新；过期报告有提示。
6. 360px 手机宽度、软键盘展开与桌面布局可用；导航不遮挡保存按钮。
7. 后台重连或首页刷新不清除尚未保存输入，不触发重复 AI 计费。
8. 新主页启用前保留空白首页的原有验收；正式切换时更新产品设计和 UI 测试，避免两套要求同时生效。

## 9. 领域深化的最小范围

| 模块 | 建议先补 | 暂缓 |
| --- | --- | --- |
| 学习 | 时长、主题、成果链接、复盘；周期计划 | 自动评价知识掌握度 |
| 饮食/锻炼 | 人工输入食物/份量/营养来源；训练项目/组次/重量；体重观测 | 无依据的图片精确估热量、自动训练处方 |
| 财富 | 收入/支出/转账分开，金额精确值、币种、账户、分类；资产快照注明日期 | 直接把任意“收获数字”当净资产、混币种求和 |
| 娱乐/交际 | 活动、时长、参与对象的可选称呼、用户主观体验 | 模型替用户判定关系质量 |

先完成可解释的记录和查询，再加自动化。营养缺失字段保持未知，金额不能使用浮点求和，跨币种汇总需汇率来源与日期。专业模板与通用模板并存，避免强迫所有记录填写复杂表单。

## 10. 协作与交付方式

建议继续一个集成负责人控制 API/数据库/契约/lockfile，前端任务按目录交付，模型适配/夹具作为独立小任务。此处只安排职责，不在本轮派发 agent 或开始写应用。

每张任务卡固定：基准提交、只读输入、允许修改路径、接口、反例与验收命令、输出日志。先完成 S0-A 冻结契约，再推进依赖该契约的页面；纯视觉组件可以并行。费用控制依靠短任务和可执行验收，避免让每个 agent 重读全仓或重复运行付费模型。

下一次开发的推荐范围是 **S0 全部 + S1 的持久草稿和稳定提交**。该批完成后先用真实日常记录试用，再决定主页组件优先级与专业模板的细节。
