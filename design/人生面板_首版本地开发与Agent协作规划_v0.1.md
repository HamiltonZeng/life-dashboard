# 人生面板：首版本地开发与 Agent 协作规划 v0.1

**日期：2026-10-19｜状态：开发前规划，尚未创建应用代码或启动容器**  
**目标目录：`/Users/zhk/life_dashboard/`｜首版应用目录：`v0.1/`｜设计文档：`design/`**

本规划更新此前 VPS 优先路线：首版先在本机 Docker 中运行和储存，后续再迁至 VPS。产品结构仍以《产品设计文档 v0.2》为准：首页空白、五个面板、四个默认模块、自定义模块、任务与记录关联、AI 模块蓝图自动填充。

## 1. 建议采用的协作方式

**一个集成负责人、一个前端负责人、一组按需调用的低耦合任务。不要同时让三个 agent 各自设计整套应用。**

优先利用已经购买的订阅做开发；额外 API 调用用于有明确输入、输出和验收的小任务。数据库和后端核心由同一负责人连续掌握，避免每次跨 agent 交接都重新解释数据约束。

| 角色 | 建议入口 | 负责范围 | 文件所有权与交付 |
| --- | --- | --- | --- |
| 架构、数据库、后端与最终集成 | 用现有 ChatGPT 账号登录的 Codex | 数据模型、迁移、API 契约、真实记录与任务联动、同步、鉴权、后台任务、整体验收 | `apps/api`、`apps/worker`、`packages/db`、`packages/contracts`、`packages/domain`、`packages/sync-core`、部署配置 |
| 前端与移动体验 | 若你的订阅确为 Google AI Pro，使用该账号登录 Gemini CLI 或相应开发工具 | 空白首页、五个面板、模块筛选、记录表单、关联跳转、响应式与错误状态 | `apps/web`、`packages/ui`；依照冻结契约，不自行修改数据库 |
| AI 适配与确定范围的小任务 | DeepSeek API 驱动的开发工具；工具尚未选定时可先交付补丁 | DeepSeek 适配器、蓝图验证、测试夹具、固定格式转换、边界清晰的测试与文档 | 每次指定目录，例如 `packages/ai` 或 `tests/ai`；不默认整个仓库可写 |
| 独立检查 | 与实现者不同的 agent 按需承担 | 检查变更、补充关键反例和界面走查 | 默认只读，输出可复现问题；修复交还对应负责人 |

这是初始分工假设，不是“某品牌天然最擅长前端／后端”的能力排名。先用一两个小任务观察首次验收通过率、修正轮数和实际额度，再调整分工。如果 Gemini 只有网页聊天可用，它可以先提供原型与有限代码建议，实际仓库执行由具备文件和终端能力的 agent 承担。

**数据库不单独开一个长期并行 agent。** 主负责人先完成数据库与契约阶段，再推进后端；前端基于契约和假数据并行。数据库迁移、同步协议、幂等和财务一致性不作为无人复核的低价外包任务。

## 2. 订阅、API 与成本边界

### 2.1 先用已付订阅，不预设无限额度

OpenAI 官方文档区分 ChatGPT 登录的订阅访问和 API Key 的按量访问。开发时优先使用现有账号在 Codex 中可用的额度；若切成 API Key 登录，则按 API 路径计费。具体可用模型和剩余额度以账号界面为准，多开 agent 不会创造多份独立订阅配额。[OpenAI 官方鉴权说明](https://learn.chatgpt.com/docs/auth)｜[方案与能力](https://learn.chatgpt.com/docs/pricing)

“Gemini Pro”需要区分模型名称与 Google AI Pro 订阅。如果是 Google AI Pro，官方 Gemini CLI 文档提供 Google 账号登录的订阅额度路径；使用 Gemini API Key 则走 API 自身的免费或按量额度。这里不把聊天会员理解为任意调用 API 的通用余额。[Gemini CLI 额度与登录方式](https://geminicli.com/docs/resources/quota-and-pricing/)

DeepSeek 在应用运行时按 API 路径接入，开发 agent 是否也调用它由所选工具决定；聊天界面的可用性不作为 API 已充值、已配置的证明。[DeepSeek 官方计费说明](https://api-docs.deepseek.com/quick_start/pricing/)

### 2.2 分开计算两种 AI 开销

- **开发开销：**agent 阅读代码、修改、调试、审查所用的订阅额度或 API 费用。
- **应用开销：**你在面板里生成模块、日报和周报时调用 DeepSeek 的费用。

两者分别记账，分别设上限。首版测试默认使用可复现假数据和 mock 模型，只有接入验收时做少量真实请求；不在每次前端刷新、单元测试或截图时调用付费模型。

暂不报一个未经测量的“每月开发 token 成本”。先记录实际任务：输入输出量、缓存命中（供应商若提供）、费用或订阅用量、修正轮数、是否通过验收。根据真实样本选择模型，避免用每百万 token 单价直接推断完整任务成本。

### 2.3 降低无效消耗

1. **先冻结契约，再分头实现。** 接口反复变动造成的返工，通常比少量模型价差更值得控制。
2. **只读相关材料。** 前端读取面板规范、组件约定与接口样例；后端读取数据规则和验收；AI 任务读取蓝图 Schema、样例和适配接口。完整个人对话不作为每次 coding 的上下文。
3. **短任务卡。** 每项任务明确目标、可改文件、不可改文件、依赖、验收命令、交付格式；不要反复生成整份计划或整仓解释。
4. **机器先验证。** 先运行类型检查、Schema 校验和相关测试，再让另一个模型审查。不要让模型用长篇推测代替可运行结果。
5. **失败限次。** 同一问题连续两轮没有新增证据，暂停重试，输出最小复现和错误，再交集成负责人处理。这是初始协作规则，可调整。
6. **按风险选择推理强度。** 数据迁移、并发冲突和复杂定位使用更强推理；样式、样例数据和局部重复代码用普通档。不默认所有任务都最高档。
7. **稳定上下文与摘要。** 固定契约与 Schema 尽量稳定；任务完成后保留提交、验证结果与短交接，不传整段聊天记录。供应商缓存是否命中仍以实际响应为准。
8. **按需并行。** 首期最多两个实现任务同时写代码；第三个可以只读检查。不要让多个 agent 循环互评、不断扩张任务。

## 3. 首版本地架构

沿用 React + Vite PWA、Fastify、PostgreSQL、Drizzle、pg-boss 与服务端 DeepSeek 适配。暂缓 VPS 部署和 RAG，不为了单机先换成另一套数据库。

```text
电脑或手机浏览器
    → 本机入口代理 / Web
    → 本机 API
    → 本机 PostgreSQL 与附件文件
    → 本机 worker
    → DeepSeek 云端 API（仅授权范围）
```

这里“本地运算储存”默认指业务逻辑、统计、数据库、附件和任务调度在本机；DeepSeek API 仍需网络并把选定输入发往供应商。若关闭云端 AI，其他功能和模板日报仍可使用。完全本地大模型是另一项硬件与模型部署决策，本次不自动加入。

### 3.1 Docker 中运行什么

开发工具链、依赖安装、代码构建、类型检查、测试、API、worker 和 PostgreSQL 都在容器内运行。宿主机保留编辑器、Git、Docker 和你使用的 agent 客户端；agent 可以在宿主机读写源码，但执行项目命令应通过开发容器。

建议开发 Compose 包含：

- `web`：Vite 开发服务，热更新。
- `api`：Fastify 开发服务。
- `worker`：任务处理，真实 AI 默认关闭，使用 mock。
- `postgres`：本地持久化主库。
- `gateway`：统一入口，处理 Web、API 和需要的 HTTPS。
- `tools`：按需运行安装、检查、迁移和测试，不必一直常驻。

不安装到宿主机的全局 Node/Python 环境，不把 Docker 容器可写层当作唯一数据存放位置。开发容器不是对拥有 Docker 权限的 agent 的完整安全隔离；不默认把宿主机整个家目录或 Docker socket 暴露给所有任务容器。

### 3.2 手机使用的现实条件

电脑与手机处于可互通网络、Docker 正在运行时，手机可连接本机入口。默认开发服务只绑定本机；需要手机联调时再明确开放受限局域网入口，不直接暴露数据库。

桌面 `localhost` 的安全上下文不能直接套用到手机访问电脑的局域网 IP。要验收手机 PWA、Service Worker 与部分浏览器能力，需要手机信任的 HTTPS；规划使用本地证书和明确的设备信任流程，不能将普通局域网 HTTP 页面当作完整 PWA 验收。[MDN 安全上下文](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)

电脑关机、休眠或 Docker 停止后，手机仍可在已缓存且存储可用的前提下离线记录；同步、服务器报告和跨设备查看需等本机恢复。首次打开尚未缓存的网页，不能在服务器离线时保证可用。

应用版本 `v0.1` 与产品设计文档版本 `v0.2` 是两个维度，不需要把产品设计文件改名成应用版本。

### 4.2 可控缓存全部留在当前版本

将包管理器 store、Corepack/npm 缓存、Vite/TypeScript 构建缓存、浏览器测试下载与结果、应用自管的 AI 响应缓存等路径明确配置到 `v0.1/.runtime/cache` 或同版本目录。只调整项目／容器级变量，不改宿主机 HOME、全局 pnpm 设置或其他项目缓存位置。

依赖安装产物和编译产物也放在当前版本树中；容器内固定路径通过 bind mount 映射到这些目录。容器默认临时文件和库的默认缓存行为要在 T0 验证，不能只建了 `.runtime/cache` 就声称全部路径已受控。[Docker bind mount 说明](https://docs.docker.com/engine/storage/bind-mounts/)

### 4.3 不能混为“缓存”的内容

| 类别 | 存放与处理 |
| --- | --- |
| PostgreSQL 数据、真实附件 | `.runtime/data`，属于持久数据，不能通过清缓存删除 |
| 数据库备份和可恢复导出 | `.runtime/backups`；同盘备份只应付误操作，另行保留异机副本 |
| 密钥和本地证书 | `.secrets` 或专门私密配置，权限受限，不进入普通缓存、日志和源码提交 |
| Docker 镜像与 BuildKit 缓存 | 默认由 Docker Engine／Docker Desktop 管理，无法仅靠项目环境变量全部转进版本目录；不在此阶段迁移 Docker 全局数据目录 |
| 手机和电脑的 IndexedDB、Service Worker 缓存 | 浏览器按设备和 Origin 管理，不能指定保存到电脑项目文件夹 |
| 模型供应商的提示缓存 | 属于供应商侧行为，本地目录只管理应用自有的响应缓存，不能把供应商缓存迁到本地 |
| agent 的登录态、客户端全局历史 | 由相应工具或系统凭据存储管理，不复制认证文件进项目；仅任务摘要与测试产物按版本保存 |

因此，可实现的约定是：**当前应用版本能控制的缓存和运行产物都落在版本目录；系统、浏览器和供应商层缓存明确列为外部例外。** 不把“清理缓存”设计成删除整棵 `.runtime`。

### 4.4 版本隔离与数据迁移

Compose project name 显式设为类似 `life-dashboard-v0-1`，不依赖 `v0.1` 的目录名生成；后续版本用不同名称、端口、文件卷和浏览器存储标识。项目名称规则与隔离行为见 [Docker 官方文档](https://docs.docker.com/compose/how-tos/project-name/)。

PostgreSQL 数据与上传文件使用版本内明确 bind mount，路径按选定 PostgreSQL 镜像的官方要求配置；不靠匿名卷隐藏实际数据位置。数据库目录不复制到多个正在运行的实例中共享。

浏览器侧按版本设置数据库名和缓存名，并采用不同 Origin 或隔离路径与 Service Worker scope 的策略验证；仅仅改容器名称不能隔离浏览器缓存。手机端同样受此规则影响。

未来 `v0.2` 不复制 `.runtime` 整目录：从 Git／发布源码建立新版本，重新安装依赖，先导出数据、备份并演练迁移，再启用。新旧版本不能随意同时修改同一数据库。Git 用来管理代码历史，版本文件夹只做你需要的运行环境与交付边界。

## 5. 开发前先冻结的契约

先由集成负责人完成最小契约，作为其他 agent 的共同输入：

1. 模块、模板、记录、任务模板／实例、数值定义、成就定义／授予、AI 生成批次的数据结构与 ID 规则。
2. 核心 API 的请求、响应、错误、分页、时间、单位和状态枚举。
3. 任务到记录的关联、保存后的状态传播、修改／删除后的重算。
4. AI 蓝图 Schema、引用命名、应用事务和重复提交幂等。
5. 最小登录／本地账户、设备与同步边界，决定首版哪些接口必须先具备。
6. 假数据样例与约定的验收命令。

前端基于契约和 mock 开始，不等待全部后端完成。只有集成负责人修改共享契约与主 lockfile，其他 agent 提交变更需求。迁移按顺序编号与评审，不让两个任务各自生成冲突迁移。

## 6. 首版按纵向闭环交付

每个阶段完成后再扩大范围，避免五个面板都画好了却没有一个真实流程可用。

| 阶段 | 交付 | 主负责与并行方式 | 验收关口 |
| --- | --- | --- | --- |
| T0：环境与契约 | Docker、版本路径、最小数据库迁移、健康检查、mock 契约 | Codex 主责；Gemini 可先做只读视觉方案 | 容器内安装与测试成功；重启后数据仍在；文件落点清楚 |
| T1：第一条真实闭环 | 空白首页、五面板导航、四模块；任务 → 记录 → 数值 → 成就 | Codex 后端与 DB；Gemini 前端并行 | 用真实写库记录完成一次闭环，刷新后保留；无假事实 |
| T2：配置能力 | 自定义模块、模板、任务完成方式、受限数值规则、成就条件、设置 | 前后端按各自目录；DeepSeek 可提供明确夹具 | 新模块不改代码即可参与四类内容，依赖检查有效 |
| T3：DeepSeek 接入 | 密钥配置、生成并添加、校验、原子应用、重试与撤销 | DeepSeek agent 负责受限适配任务；Codex 接入与复核 | mock 先通过，再少量真实 API；失败不留下半套配置 |
| T4：本地可日用 | 本地持久化、手机 HTTPS、离线队列、同步冲突、备份导出 | 集成负责人主导；Gemini 修手机体验 | 断网、刷新、重启和重复提交不丢失或重复累计 |
| T5：首版发布 | 日报周报基础、关键测试、数据恢复、启动说明与版本记录 | 一个 agent 集成，另一个独立审查 | 一键启动方案、恢复演练、已知限制和可复现验证结果齐全 |

T1 可以先使用在线记录，但不能把它宣布为已满足手机随时离线记录的首版；最终验收要走完 T4。学习、娱乐等通用记录可先跑通闭环，饮食与财富逐步增加专业表单，不为赶工把普通数字字段包装成可靠营养算法或账本。

首版暂缓原生 App、复杂营养识别、跨模块复杂成就和向量 RAG；保留接口与原始数据。日报周报先用确定性统计和少量相关文本，不需要向量数据库才能交付。

## 7. 多 agent 怎样交接和合并

### 7.1 单任务卡模板

```text
任务 ID / 目标：
基准提交或契约版本：
只读输入：
允许修改的路径：
禁止修改的路径：
预期接口与状态：
必须通过的验收命令：
完成后交付：提交 ID、变更文件、验证结果、未解决问题
遇到契约变化：停止该依赖部分，提具体变更建议
```

### 7.2 执行规则

- 一个任务一个分支／隔离工作树，不在同一工作目录让两个 agent 同时安装依赖、改 lockfile 或跑迁移。
- 工作树可放在当前版本 `.runtime/worktrees` 下，自己的依赖与缓存也在各自目录中；主数据只给集成环境，测试用独立数据库。
- 主工作区由集成负责人控制。前端与后端任务完成后，以提交或补丁交付，先看 diff 和相关测试，再合并；不复制一整份未知状态目录覆盖主工作区。
- 容器测试使用测试数据库与假附件，不能连接用户真实数据库后执行清库脚本。
- 审查默认只读，不擅自把问题扩展成全仓重构；只在发现新问题或新变更时扩大测试。

此阶段不指定必须安装某个多 agent 编排平台。现有 Codex、Gemini CLI 和按需 DeepSeek 工具配合短任务卡即可开始，减少额外 API 和平台成本。不同产品中的 agent 不会因为同在这台电脑就自动协调；文件所有权、任务状态和合并负责人必须显式约定。

## 8. 开发开始前的准备清单

你确认开始后，第一批工作应限于：

1. 将项目目录作为实际开发工作区，读取届时存在的项目约定；设置 Git 与忽略规则。
2. 核查 Docker 与所选 agent 工具可用状态，不在此规划阶段擅自安装。
3. 建立版本内源码与运行目录，编写 Docker 开发配置和路径说明。
4. 冻结最小 API／数据库契约，建立不含私人信息的假数据。
