## 7. 新发现的 5 个缺陷

优先级定义：P1 为接入付费模型前应完成的稳定性/额度控制修复；P2 为本轮质量收口应修复的业务与接口问题。以下均已复现，未在本轮修改实现。

### R1 · P2：按模块查询 AI 批次返回 500

定位：[AI service.ts:399](/Users/zhk/life_dashboard/v0.1/packages/ai/src/service.ts:399)。

`listBatches` 的列表 SQL 用 `$4` 表示 module_id，统计总数时复用了相同条件，却只传 `[user, module_id]`。因此合法请求 `GET /api/v1/ai/batches?module_id=<模块 UUID>` 返回 `500 INTERNAL_ERROR`，空批次库也会触发。

修复要求：统计 SQL 使用对应的 `$2` 或统一生成独立参数列表；回归覆盖无筛选、有筛选、空结果和分页 total。

### R2 · P1：并发 AI 生成可突破每日任务上限

定位：[AI service.ts:89](/Users/zhk/life_dashboard/v0.1/packages/ai/src/service.ts:89)。

配额检查先 count，再插入任务；两步没有原子预留。同一用户两个请求可先后读到相同剩余额度，再同时创建任务。隔离复现把上限设为 1，控制两个计数都先完成，最终 **2 个生成请求均成功**。

这证明当前 `AI_DAILY_JOB_LIMIT` 不能作为严格费用保护。它还是滚动 24 小时任务数限制，不是人民币费用预算；重试和 token 成本需另行建模。

修复要求：在用户锁或专用额度行事务中完成检查与任务预留，外部模型调用放在事务外；失败释放、重试计费与用量结算明确分开。回归要求上限 1 时并发两请求只允许一个创建。

### R3 · P2：撤销后的任务仍能通过手动完成接口复活

定位：[API service.ts:94](/Users/zhk/life_dashboard/v0.1/apps/api/src/service.ts:94)，撤销写取消状态见 [AI service.ts:444](/Users/zhk/life_dashboard/v0.1/packages/ai/src/service.ts:444)。

完成接口验证模块、版本和完成方式，但未拒绝 `cancelled`。复现：向仍启用的现有模块应用一组 AI 配置，创建引用记录后撤销批次，使其中 manual 任务被取消；取得最新版本后再调用完成接口，返回 200，状态变回 completed。

修复要求：集中定义任务状态迁移，取消状态拒绝完成；即使前端隐藏按钮，服务端仍需防守。测试同时覆盖 record_optional 和重复完成语义。

### R4 · P2：新成就可以引用已归档的数值定义

定位：[API service.ts:111](/Users/zhk/life_dashboard/v0.1/apps/api/src/service.ts:111)。

创建成就只校验 metric 的用户与模块，没有 `archived_at IS NULL`。复现：撤销扩展批次后，该数值已归档；手动用其 ID 新建成就仍返回 200，bootstrap 有活动成就，却没有活动来源数值。

历史 D3 解决的是“撤销时归档已有依赖成就”；本问题是“撤销后还能新建依赖”，属于另一条写入路径。

修复要求：所有引用入口统一校验活动状态；拒绝已归档来源，正式测试应断言无悬挂活动定义且失败原子回滚。

### R5 · P1：模型超时未覆盖响应体读取

定位：[adapter.ts:60](/Users/zhk/life_dashboard/v0.1/packages/ai/src/adapter.ts:60)，计时器清除位于 [adapter.ts:82](/Users/zhk/life_dashboard/v0.1/packages/ai/src/adapter.ts:82)。

`fetch` 获得响应头后便在 finally 清掉超时计时器，随后 `response.text()` / `response.json()` 不受该计时器约束。复现给适配器传 10ms 测试超时，立即返回响应头、延迟 120ms 发送 body，实际约 136ms 后仍成功。该数值为适配器级注入测试；环境配置的最小超时为 1000ms，同一控制流问题仍然成立。

修复要求：计时器覆盖完整请求、body 读取与错误解析；超时归一到 `AI_TIMEOUT`。测试包括慢响应头、慢正常 body、慢错误 body 和中途断流。

另外，配置允许 10s × 3 次尝试，和文档“最坏情况低于 API 15s”的说法不一致；Fastify `requestTimeout` 也不能当作业务处理完成的统一截止时间。应建立明确的模型尝试时限与任务总时限，后续转后台执行。

## 8. 尚未覆盖的验证与维护风险

1. **浏览器测试不可重复**：历史日志记载 27+5 项 Edge/CDP 检查，但脚本未入库；Gemini 的 P01–P11 视图断言也没有对应仓库测试文件。它们是历史执行自述，当前仓库不能一条命令复跑。需要正式 UI 测试，而不是用 API 测试代替。
2. **前端规模集中**：`main.ts` 1692 行、`panels.ts` 2422 行，主界面通过整体 innerHTML 渲染。增加主页、同步状态和报告前建议按面板/表单/AI 流程拆分；避免全量重绘丢失尚未保存输入。
3. **状态只在内存**：筛选/返回上下文、显示设置没有完整持久化方案，也没有断网草稿与待同步队列。刷新恢复不等于服务器已存记录恢复。
4. **全量读取与重算**：列表读取 snapshot 后内存分页，多数写操作同步重算相关全量事实/定义。小数据可用，但未证明长期大数据下的响应时间。先按 1千/1万/10万条合成记录测量，再按结果改 SQL 聚合、索引和派生缓存。
5. **蓝图与正式定义存在字段落差**：任务说明/优先级/预计时长以及模板说明未存入正式定义，部分会 warnings；数值 description/proposed_target 也未进入正式数值定义。候选中保留原值不等于产品已支持目标管理。应明确支持矩阵，避免用户以为全部已自动填入。
6. **无发布基线**：Git 尚无提交，项目文件整体处于未跟踪状态。缺少可比对的基准提交，不能可靠归因到某次 agent 修改。修复并验收后应建立首个基线提交；本轮未擅自创建提交。
7. **运行边界仍为本机开发**：入口绑定 127.0.0.1；没有正式账号、设备管理、可信手机 HTTPS 或恢复演练。不能仅把端口开放就视为完成远程部署。
